# Confidential Engineering PDF Design

**Status:** design proposal only — no implementation, migration, bucket, schema, or production change is authorized by this document.  
**Date:** 2026-08-20  
**Proposed repository location:** `docs/audits/CONFIDENTIAL-ENGINEERING-PDF-DESIGN.md`

## 1. Current integration baseline

PR #45 has now been merged into `develop`, so the confidential-PDF design can target the current authenticated membership/onboarding model directly.

The cryptographic model depends on Supabase Auth and the existing `docinspector_profiles` / `docinspector_workspace_members` authorization plane. The access-request flow is only an onboarding mechanism; it is not a cryptographic root of trust.

Therefore:

- PDF E2EE must use real authenticated membership as the authorization baseline;
- no PDF key may be derived from the 12-character access-request code;
- no PDF key may be derived from the legacy `sky17_*` workspace secret;
- implementation must start only after this design is explicitly approved;
- implementation must branch from the then-current `develop`;
- crypto, metadata/RLS, encrypted Storage transport, PDF.js/offline cache, recovery and rotation remain separate small PRs.

## 2. Security objective and threat model

Engineering PDFs are confidential. Supabase Storage, Postgres, service-role code, backups, database operators, and a Storage compromise must reveal only ciphertext and non-secret routing metadata.

The server must never receive:

- PDF plaintext;
- a workspace content-encryption key in plaintext;
- a per-file content-encryption key in plaintext;
- a member private encryption key in plaintext;
- a recovery secret capable of reconstructing those keys.

The design protects **data at rest and in server-side transit/storage** from the application backend. It does not make an already-authorized endpoint magically safe from:

- screenshots or photography;
- a user explicitly exporting a plaintext PDF;
- malware/browser extensions on a device after decryption;
- a stolen unlocked device that still contains usable client-side key material;
- malicious JavaScript delivered by a compromised application origin.

The last point is inherent to browser E2EE: if an attacker can replace the DocInspector JavaScript itself, it can exfiltrate keys after the user decrypts them. Production hardening should therefore self-host and pin cryptographic/PDF dependencies, use a restrictive CSP, avoid runtime third-party scripts on the sensitive view, and keep releases auditable.

Revocation also cannot erase information already decrypted or copied by a former authorized member. Rotation protects future access and prevents new server-side retrieval, but cannot make a prior plaintext copy disappear.

## 3. Chosen key hierarchy

Use client-side envelope encryption with three levels:

1. **Member Encryption Key Pair (MEK)** — account-level asymmetric key pair.
2. **Versioned Workspace Key (WK)** — random symmetric key shared only with currently authorized members.
3. **Per-file File Encryption Key (FEK)** — random symmetric key unique to each PDF.

### 3.1 Member Encryption Key Pair

For v1, use Web Crypto `RSA-OAEP` with SHA-256 and a 3072-bit modulus.

Why RSA-OAEP for v1:

- Web Crypto support is mature across the browsers DocInspector already targets;
- it only wraps small key material, so RSA performance/size is acceptable;
- it avoids depending on newer X25519 browser support for the first implementation;
- no custom cryptographic library is required for key wrapping.

Generation happens **only in the browser** after a real Supabase Auth session exists.

The public key may be stored in Postgres. The private key must never be uploaded in plaintext.

### 3.2 Private-key recovery backup

A new member also receives a 256-bit random **Recovery Secret (RS)** generated client-side. It is displayed once and the user is instructed to store it in a password manager or controlled offline record.

The browser:

1. generates the MEK;
2. exports the private key only during enrollment;
3. derives a backup-encryption key from RS using HKDF-SHA-256 with a random salt and context binding;
4. encrypts the private-key export with AES-256-GCM;
5. uploads only the encrypted private-key backup + salt/IV/version metadata;
6. imports/retains a non-extractable local `CryptoKey` for normal use;
7. discards plaintext export buffers on a best-effort basis.

The server never sees RS, so it cannot decrypt the private-key backup.

A human password must **not** be the sole cryptographic recovery secret in v1 because a server-side encrypted backup allows offline guessing if the password is weak. If a friendlier recovery UX is desired later, a passkey/WebAuthn PRF design can be evaluated separately.

### 3.3 Workspace Key

Each workspace has a versioned random 256-bit WK generated by an authorized client.

WK plaintext is never stored server-side.

For each authorized member, the client encrypts the WK to that member's RSA-OAEP public key. Postgres stores one **workspace-key envelope** per member/key version.

A client retrieves only its envelope, decrypts it locally using its MEK private key, and imports the resulting WK as an AES key.

The 12-character access-request code and the legacy `sky17_*` workspace secret are never used to derive WK.

### 3.4 File Encryption Key

Each PDF receives a fresh random 256-bit FEK.

The PDF is encrypted with FEK using AES-256-GCM. FEK itself is then encrypted under the current WK with AES-256-GCM and stored as ciphertext metadata.

This extra FEK layer is important: workspace-key rotation can re-encrypt only the small FEK envelopes rather than uploading every large PDF again.

## 4. PDF encryption format

Use a versioned encrypted container rather than uploading a normal `.pdf`.

Recommended object content type: `application/octet-stream`.

Recommended logical format: `DIPDF1`.

For an initial maximum 20 MiB PDF, encrypt in 1 MiB chunks:

- every chunk uses AES-256-GCM;
- every chunk gets a cryptographically random 96-bit IV;
- IVs are stored beside ciphertext;
- authenticated additional data binds at least:
  - crypto format version,
  - workspace ID,
  - inspection ID,
  - file ID,
  - chunk index,
  - total chunk count.

AES-GCM therefore provides both confidentiality and tamper detection. Reordering, substituting, or modifying a chunk causes decryption failure.

The original filename, title, description and similar business metadata should also be encrypted. The server only needs opaque IDs, object routing information, key version, ciphertext size/hash, creator ID and timestamps.

A SHA-256 hash of the **ciphertext** may be stored server-side for transport/cache corruption detection. It is not a plaintext fingerprint.

## 5. Proposed server-side metadata (all keys remain ciphertext)

Exact SQL belongs to a later approved migration, but the design expects four logical stores.

### Member public keys

`docinspector_member_public_keys`

- `user_id`
- `key_id`
- public RSA JWK
- client-computed fingerprint
- status / created / rotated / revoked timestamps

Active workspace peers may need read access to a member's public key so an authorized client can create a WK envelope.

### Member encrypted key backups

`docinspector_member_key_backups`

- `user_id`
- `key_id`
- encrypted private-key backup
- HKDF salt
- AES-GCM IV
- crypto format version

RLS: owner-only read/write. Administrators and service-role code do not need to decrypt it.

### Workspace key versions and envelopes

`docinspector_workspace_crypto_keys`

- workspace ID
- key version
- state (`ACTIVE`, `ROTATING`, `RETIRED`)
- timestamps / actor IDs only

`docinspector_workspace_key_envelopes`

- workspace ID
- WK version
- recipient user ID
- recipient member-key ID
- RSA-OAEP wrapped WK
- algorithm/version metadata

RLS should allow a recipient to read its own envelope. Authorized key managers may create envelopes for active members, but no backend function receives WK plaintext.

### Project PDF metadata

`docinspector_project_documents`

- opaque file ID
- workspace ID
- inspection ID
- Storage object path
- crypto format version
- WK version used for the FEK envelope
- encrypted FEK + IV
- encrypted filename/metadata + IV
- ciphertext byte size
- ciphertext SHA-256
- creator / timestamps / logical deletion state

The PDF bytes themselves stay out of the inspection JSON payload and out of Postgres. The relationship to an inspection is normalized by `inspection_id`.

## 6. Adding a member

Membership and cryptographic access are separate states.

A newly invited/approved Auth member does not automatically receive WK plaintext.

Flow:

1. member authenticates;
2. member enrolls/generates MEK and publishes its public key;
3. an existing authorized keyholder (normally ADMIN) sees a pending key grant;
4. that ADMIN client decrypts WK locally;
5. ADMIN client wraps WK to the new member public key;
6. only the wrapped envelope is sent to Supabase;
7. new member can now decrypt PDFs.

Until a valid envelope exists, the member should be treated as **crypto-not-ready** for confidential PDFs.

Storage RLS can optionally require both active membership and existence of a current WK envelope before allowing ciphertext download. This avoids serving even ciphertext to a membership that has not completed E2EE provisioning.

## 7. Removing a member and rotating keys

Removal is a security event and must be online.

Recommended sequence:

1. deactivate workspace membership first so RLS blocks new Storage/metadata retrieval;
2. a remaining authorized ADMIN client generates `WK n+1`;
3. client wraps `WK n+1` to every remaining authorized member;
4. for every existing PDF:
   - decrypt its FEK envelope locally with old WK;
   - encrypt the same FEK under `WK n+1`;
   - update only the FEK envelope metadata;
5. mark `WK n+1` active after all required envelopes are committed;
6. retire old WK metadata.

The large encrypted PDF object does not need re-uploading.

**Limitation:** if the removed member previously cached the old encrypted file *and* its usable old key/envelope, no cryptographic scheme can make that already-acquired copy unreadable. Rotation prevents future server retrieval and protects future key versions/files.

If a high-assurance incident requires re-encrypting existing server objects with new FEKs, that can be an explicit maintenance operation, but even this cannot revoke a plaintext or old ciphertext/key copy already possessed by the removed member.

Rotation must be resumable. A `ROTATING` state should allow the client to continue after interruption without leaving files inaccessible.

## 8. Lost or replaced device

### User has Recovery Secret

1. user signs into Supabase Auth on the new device;
2. downloads encrypted private-key backup;
3. enters/scans RS locally;
4. browser reconstructs MEK locally and stores a non-extractable key;
5. old Auth sessions are revoked;
6. if the lost device is considered compromised, rotate the member key and WK so future documents no longer use material known to that device.

### User has no Recovery Secret but another trusted ADMIN exists

The user creates a new MEK on the replacement device. After identity/membership verification, an existing ADMIN client grants the current/new WK to the replacement public key.

For a potentially compromised lost device, perform WK rotation rather than merely issuing another envelope.

### Sole keyholder loses every device and RS

The encrypted PDFs are intentionally unrecoverable. A server-side "master recovery key" would violate the E2EE requirement.

Operational mitigation:

- require RS acknowledgment during enrollment;
- encourage at least two active ADMIN keyholders for important workspaces;
- add an administrative warning before removing the last independent keyholder.

## 9. Supabase Storage design

Use a **new private bucket**, not `docinspector-evidence`.

Proposed name: `docinspector-confidential-pdfs`.

Reasons for a separate bucket:

- different threat model;
- ciphertext MIME type rather than images;
- independent file-size restriction;
- independent RLS;
- independent cache/lifecycle policy;
- prevents accidental treatment as evidence or public preview material.

Object path:

`<workspace_id>/<inspection_id>/<opaque_file_id>.dipdf`

Never put the original filename in the Storage path.

Bucket properties:

- private;
- allow `application/octet-stream`;
- encrypted-object size limit sized for a 20 MiB plaintext file plus container overhead;
- no public URL path.

Supabase private-bucket downloads remain subject to RLS. RLS on `storage.objects` must require active Auth membership for the workspace encoded in the path. Read should align with `VIEW_DOCUMENTS`; upload/delete should align with the already-defined `MANAGE_PROJECT_FILES` capability (currently ADMIN/INSPECTOR), enforced authoritatively server-side rather than trusting the browser capability check. Service-role access must never be used as a way to decrypt content.

## 10. Initial product limits

Proposed v1 limits:

- **20 MiB plaintext maximum per PDF**
- **10 PDFs maximum per inspection**
- **200 MiB plaintext aggregate maximum per inspection**

Rationale:

- the current Supabase Free project has a global Storage object limit ceiling of 50 MB, so 20 MiB leaves safe headroom;
- PDF.js + browser decryption temporarily need additional client memory;
- mobile Safari/Chromium should not be forced to hold extremely large engineering files in memory;
- 10 × 20 MiB bounds accidental storage explosion while still supporting a realistic document pack.

The implementation should enforce:

- file extension/type preflight only as UX, not security;
- actual PDF signature (`%PDF-`) **client-side before encryption**;
- plaintext size client-side before encryption;
- ciphertext object size via bucket restriction;
- document count/aggregate limit transactionally in authenticated server metadata logic.

Limits can be raised later with telemetry and device testing.

## 11. Offline rendering with PDF.js

Bundle a pinned, self-hosted PDF.js build with DocInspector. Do not load the viewer or worker from a runtime CDN.

The Service Worker should cache only static PDF.js application assets:

- viewer code;
- worker;
- CSS;
- fonts/CMaps required by the chosen build.

Confidential document bytes should not be placed in generic CacheStorage.

For **Disponibilizar offline**:

1. download the encrypted `.dipdf` object while authenticated;
2. store **ciphertext only** in an application-managed IndexedDB/OPFS cache keyed by workspace/file/version;
3. retain encrypted FEK metadata needed for local decryption;
4. never persist a decrypted PDF in CacheStorage or IndexedDB.

For viewing:

1. locate encrypted object locally, otherwise fetch it with Auth/RLS;
2. unwrap WK locally;
3. decrypt FEK locally;
4. decrypt PDF chunks in browser memory;
5. assemble a transient `Uint8Array`/`Blob`;
6. render with PDF.js from the decrypted bytes;
7. revoke object URLs and drop plaintext buffers when the viewer closes.

For the 20 MiB v1 ceiling, full transient decryption is simpler and more reliable than inventing a custom range source. A later version can stream/decrypt ranges if field devices show memory pressure.

## 12. Optional device download

Expose two separate actions:

- **Disponibilizar offline** — stores ciphertext inside DocInspector; preferred for field use.
- **Baixar PDF** — explicit user action that decrypts in the browser and creates a normal plaintext PDF download.

The second action must display a warning: once saved to the OS Downloads/filesystem, the plaintext file is outside DocInspector's E2EE/cache controls. OS disk encryption, MDM and user handling become the security boundary.

## 13. Service Worker and logout behavior

The Service Worker must never log, inspect or rewrite decrypted bytes.

On logout:

- clear all in-memory WK/FEK material;
- revoke viewer object URLs;
- stop confidential document rendering;
- encrypted offline ciphertext may remain, because it is E2EE;
- local private key handling must follow the approved device-security policy.

A normal PWA cannot remotely erase an already-lost device. Lost-device protection therefore combines Auth session revocation with key/WK rotation for future confidentiality.

## 14. Migration plan (future implementation only)

A future, separately approved database migration should:

1. create the application crypto metadata tables;
2. enable RLS on every new public/exposed table;
3. add minimal grants to authenticated users only;
4. add `storage.objects` RLS scoped by workspace membership and crypto readiness;
5. add server-side metadata constraints/count enforcement without any plaintext key handling;
6. add indexes for workspace/member/file lookups;
7. run Supabase Security Advisor after migration;
8. ship no service-role secret or decrypt capability to the browser.

**Bucket provisioning must not be implemented by directly inserting/updating Supabase's internal `storage` tables.** Current Supabase guidance treats the Storage schema metadata as read-only for object/bucket operations. The private bucket must therefore be created/updated through the supported Storage API/CLI as an idempotent, version-controlled deployment step paired with the migration and documented in the same release/rollback plan.

The deployment gate must verify the bucket is private, uses the intended ciphertext MIME restriction and file-size limit before enabling the UI.

No schema, policy or bucket is changed by this design document.

## 15. Rollback plan

Rollback must preserve user data.

Before the feature is generally enabled:

1. disable the PDF attachment UI;
2. stop creation of new crypto metadata/uploads;
3. preserve encrypted Storage objects and metadata while rollback is assessed;
4. restore previous RLS/policies if the migration changed shared objects;
5. keep the private bucket in read-only/preserved state while any required encrypted PDFs remain;
6. delete the bucket through the supported Storage API only after it is confirmed empty and data deletion has been explicitly approved;
7. remove new application tables/policies only after the same data-retention check.

If encrypted PDFs already exist, **do not drop the bucket or key-envelope tables as a normal rollback**. That would be destructive data loss. The safe rollback is feature-disable/read-only preservation until an explicit export/migration/deletion decision is approved.

## 16. Required automated gates before implementation can ship

At minimum:

### Crypto unit tests

- RSA-OAEP member envelope wrap/unwrap;
- wrong member key cannot unwrap WK;
- AES-GCM FEK envelope round trip;
- chunk encryption/decryption round trip;
- modified/reordered/truncated chunk fails authentication;
- wrong workspace/file AAD fails;
- recovery backup round trip;
- wrong Recovery Secret fails;
- rotation rewraps FEK without changing PDF ciphertext.

### Storage/RLS integration tests

- non-member cannot list/read/upload/delete;
- member without crypto envelope cannot download if crypto-ready gating is adopted;
- authorized reader can download ciphertext only;
- authorized writer can upload;
- forbidden role cannot write/delete;
- file-size restriction rejects oversized ciphertext;
- object path cannot escape another workspace.

### Browser E2E

Chromium + WebKit/mobile:

- attach valid PDF;
- reject non-PDF/oversize/count limit;
- render decrypted PDF inside DocInspector;
- refresh/reopen and render;
- offline-available encrypted document renders while offline;
- offline document remains ciphertext in persistent browser storage;
- optional plaintext download works only after explicit action;
- member removal/key rotation prevents the removed account from fetching current ciphertext/envelopes;
- replacement-device recovery succeeds with RS.

### Manual smoke gates

- real iPhone/iPad Safari rendering of a representative engineering drawing;
- Android/desktop Chromium;
- memory behavior near 20 MiB;
- real Supabase private-bucket RLS;
- lost-device/recovery rehearsal;
- two-member rotation rehearsal;
- service-worker update from previous production cache;
- plaintext-download warning and OS file behavior.

## 17. Implementation PR sequence after design approval

Do not build everything in one PR.

Suggested sequence:

1. crypto primitives + unit tests, no Storage;
2. crypto metadata migration + RLS, no PDF UI;
3. encrypted Storage upload/download transport;
4. PDF.js in-app viewer + offline ciphertext cache;
5. member provisioning/recovery;
6. member removal + resumable WK rotation;
7. final integration/hardening/smoke evidence.

Each step gets its own rollback notes and gates.

## Approval checkpoint

Before any implementation branch is created, approval must cover these design decisions:

1. **Recovery model:** 256-bit client-generated Recovery Secret with encrypted private-key backup; no server master key.
2. **Initial limits:** 20 MiB plaintext per PDF, 10 PDFs per inspection, 200 MiB aggregate plaintext per inspection.
3. **Revocation semantics:** removing a member blocks future server retrieval and triggers workspace-key rotation, but cannot erase plaintext/ciphertext+keys already acquired by that member.
4. **Offline model:** DocInspector caches only encrypted `.dipdf` bytes persistently; plaintext exists only transiently in memory for PDF.js rendering or explicit OS download.
5. **Separate private bucket:** confidential PDFs do not share `docinspector-evidence`.
6. **No production schema/storage action during design approval:** migration, bucket creation, RLS and deployment are later implementation steps with their own rollback gate.
